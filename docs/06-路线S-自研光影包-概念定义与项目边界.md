## 1. 项目定义与架构

### 1.1 一句话定位

**TacLight = 行为层(Forge 模组,决定"何时亮/什么色/多亮/朝哪") + 契约层(SSBO 二进制协议,模组→光影包的信封) + 渲染层(自研光影包,决定"光长什么样")。**

### 1.2 三层架构与数据流

```
┌─────────────────────── Forge 客户端主线程 ───────────────────────┐
│ 行为层 dev.taclight                                              │
│  · FlashlightItem / TaCZ gun_light 附件      —— 玩家拿了什么      │
│  · GunLaserReader + MuzzlePoseCapture        —— 光从枪口哪个点出   │
│  · ClientEvents(K/L 键)/ ClientLightState    —— 开/关/调试模式     │
└──────────────────────────────┬──────────────────────────────────┘
                               │ 每 tick 写一次(ClientSpotlightUploader)
                               ▼
┌────────────────────────── 契约层 (std430 SSBO, binding=7) ────────┐
│ 16B 头:lightCount / vlIntensity / flags / reserved               │
│ 96B × N 灯:posRadius·colorIntensity·dirType·cone·vlParams·cookie  │
│ (唯一真源:SpotlightBufferLayout.java,GLSL 头镜像+契约测试守护)    │
└──────────────────────────────┬──────────────────────────────────┘
                               │ GL43.glBindBufferBase(7)
                               ▼
┌─────────────────────── GPU 渲染线程(Iris/Oculus) ─────────────────┐
│ 渲染层 自研光影包 taclight-shaders                                │
│  shadow → gbuffers* → composite* → final                          │
│  在 composite 中:消费 SSBO → 表面锥光 / 体积光束 / 遮挡 / 风格层  │
└──────────────────────────────────────────────────────────────────┘
```

**关键**:模组与光影包之间**零 Java-GLSL 共享类**,只有 SSBO 这一封信。信的内容(ABI)已冻结并有两版契约测试保护;换信封格式 = 版本不兼容,所以 ABI 加 `flags` 版本位。

### 1.3 当前状态(截至 v0.8.4)

- 路线 P(iterationT 补丁)已完成并**验证通过**:绿锥取证截图 `run/evidence-greencone.png`、探针 `reserved=0x22fb` 全位通过;
- 路线 P 产物(`run/shaderpacks/iterationT 3.2.0 (taclight)` + `shader_patches/`)→ **冻结归档**,不再迭代;
- Java 侧已是"通用数据发送器",与具体光影包无耦合(唯一的包相关代码是 ShaderPackDiag 的探测,保留)。

### 1.4 为什么换成路线 S(本次决策依据)

| 维度 | 路线 P(iterationT 补丁) | 路线 S(自研包) |
|---|---|---|
| 光源渲染地位 | composite 事后叠加("滤镜贴片") | composite 照明阶段全权负责 |
| 曝光/色调映射 | 用别人的,不可控 | 自己的 ACES + 自适应曝光 |
| 阴影 | 屏幕空间遮挡(8 步)为上限 | 同样上限,但**可保留 spike 机会**(见 §3.2 特例) |
| 体积光 | 叠加在别人雾效上 | 自己的 raymarch,与雾深度一致 |
| 原创性 | 衍生自 iterationT(无 LICENSE,不能作为独立作品发布) | **100% 自写,0 行照搬** |
| 归属权 | 署名只能算"补丁" | **完整作品,公开仓库,独立发布** |
| 维护成本 | 每次 iterationT 升级都要重打补丁 | 无此问题 |
| 风险 | 已榨干价值,继续加深度意义有限 | 从零起步,但概念已验证(旧项目 B 走通过) |

## 2. 核心概念(由浅入深)

### 2.1 第一原理:渲染权在光影包

一旦 Oculus/Iris 接管渲染,屏幕上每颗像素都由光影包决定。模组**永远无法**绕过光影包直接照亮表面(原版又没有光源系统)。所以:

> 模组 = **数据提供方**(何时亮、多亮、什么颜色、从哪发射);
> 光影包 = **权威渲染方**(光衰减公式、软边、高光、遮挡、体积、曝光、色彩)。

这句是理解后续一切概念的地基,也是否定"无光影方案"的原因:没有光影包时,只能给一个**视觉光锥贴图**(V 通道兜底),无法照亮表面。

### 2.2 坐标系(本次项目最大的坑,已填)

Iris/Oculus 各阶段的模型视图矩阵约定**不同**:

| 阶段 | 坐标体系 | gbufferModelView 性质 | 含义 |
|---|---|---|---|
| gbuffers | world → view | **含平移** | 顶点阶段用 `gl_ModelViewMatrix` 正常变换 |
| composite / final | **scene-relative**(= world − cameraPosition) | **纯旋转(无平移)** | 位置数据必须先生成 scene-relative 再乘 |mat3| |
| deferred | scene-relative | 纯旋转(与 composite 同族) | 同上(Photon 的 scene_pos 即此约定) |

**规则(写死,整个项目遵守):**

1. 模组上传的灯光位置 = **world 坐标**(浮点,双精度在 Java 侧转 float);
2. **GLSL 消费时先转 scene-relative**(`scenePos = worldPos - cameraPosition`),再按阶段转 view;
3. composite 阶段 `viewPos = mat3(gbufferModelView) * scenePos` —— **禁止**把 world 坐标直接乘 `gbufferModelView`(等价于把世界原点当镜头原点,灯会被摆到几百格外,这就是 v0.8.4 之前的 bug);
4. 方向向量:world 正装上传,消费时同样 `mat3(gbufferModelView)` 旋转;
5. 投影:view → clip 用 `gbufferProjection`(composite 中有效),clip → uv 标准透视除法;
6. 自研包的**唯一纵深**:所有换算封装成两个函数 `taclight_scene_to_view()` / `taclight_view_to_uv()`,全部光照代码只调这两个入口——旧项目 B 就是这样做到"端到端 scene-relative"的。

### 2.3 距离衰减(本次指正项,正式定义)

> **定义**:衰减量 = 光源到**被照亮表面**的**游戏内 3D 距离**的函数。`d = |P_surface − P_light|`(单位:格),与屏幕、与相机朝向**无关**。

**正确表达式(已实现,语义正确)**:

```glsl
vec3 toFrag = viewPos - lightView;      // 视图空间 3D 距离(与屏幕中心无关)
float dist  = length(toFrag);
float atten = pow(max(1.0 - dist / radius, 0.0), 2.0);   // 半径归一 + 平滑衰减
```

**错误示范(禁止)**:

- ❌ 以屏幕中心距离(`length(uv - 0.5)`)做衰减 —— 那是"中心向外变暗"的径向渐变,不是光照衰减;
- ❌ 以相机深度(`-viewPos.z`)做衰减 —— 那是"越远越暗"的距离感,会把近处侧壁的错误变亮;
- ❌ 把 `d` 单位混用(米/格/缩放后长度)。

**衰减公式候选(§5 D6 待选)**:

| 公式 | 特点 |
|---|---|
| `pow(1-d/r, 2)`(当前) | 线性到半径处归零,视觉简洁,无物理含义 |
| `1 / (1 + k·d²)`,k 由半径标定(推荐) | 反平方物理感,无奇点,近距离亮、远处自然暗 |
| `pow(1-d/r, 0.5)` | 更"满",适合泛光感 |

> 体积光束的**遮挡**采样不在此列:那是沿光线的深度步进,用相机距离判断"被墙挡住",属于遮挡概念(§2.7),不许混用。

### 2.4 聚光灯(锥形光)模型

- **数据类型**:`spot = (P, R, I, dir, θ_out, θ_in)`:位置、半径、强度、朝向、外锥半角、内锥半角;
- **锥判定**:`cosAng = dot(normalize(P_frag − P_light), dir)`,软边 `spot = smoothstep(cos θ_out, cos θ_in, cosAng)` —— 内锥全亮,外锥全灭,中间线性软边(这是"手电筒感"和"原版点光球"的视觉分界线);
- **方向来源**:手持模式下 = 枪口朝向(由 MuzzlePoseCapture 录取);非枪模式 = 相机朝向;
- **点光源特例**:`dirType.w < 0.5` 时按球光处理(保留,用于火把等附件)。

### 2.5 数据通道与 SSBO ABI(冻结件)

**通道总览**(谁都能用,但兼容面不同):

| 通道 | 机制 | 兼容面 | 本项目角色 |
|---|---|---|---|
| G | `IrisItemLightProvider` → `heldBlockLightValue` | 任何实现了手持光的包 | **保留**(兜底/兼容) |
| G′ | Mixin 给 TaCZ 枪械加"光源身份"接口 | 仅本 mod | **保留**(决定枪什么时候亮) |
| S | 外部 SSBO,`layout(std430, binding=7)`,IRL 兼容 | 仅本 mod 配套包 | **主线通道** |
| V | 模组自画光锥(无光影时) | 无光影环境 | 兜底 |
| P | item.properties ID 映射 | 特定包 | 弃用(不再适配第三方包) |

**S 通道 ABI(冻结,不改)**:

```
头 16B:  uint lightCount | float vlIntensity | uint flags | uint reserved
灯 96B × N: posRadius(xyz 世界坐标, w 半径)
            colorIntensity(rgb 线性色, a 强度)
            dirType(xyz 世界方向, w 类型:1=spot)
            cone(x = cos 外锥, y = cos 内锥, z/w 保留)
            vlParams(x 各向异性, y 密度, z 光束强度)
            cookie(回写诊断用:viewPos+dist)
flags: bit0 HAS_DATA | bit1 DEBUG(绿锥调试) | bit3 TIMING_PROBE
```

三条铁律:
1. **唯一真源 = `SpotlightBufferLayout.java`**(含列偏移、flags、大小),GLSL 侧只有镜像头文件,由 `SpotlightBufferLayoutContract`(Java 契约测试)+ 打包脚本做双端一致性守护;
2. **包内不声明 `bufferObject.7`** —— 声明了 Iris 会自建同名缓冲并覆盖我们的绑定;外部 SSBO 由模组创建/绑定/每 tick 更新,包只读(已实测可行);
3. 位置**以 world 坐标上传**、GLSL 按 §2.2 规则转 scene-relative(上传侧不做变换,保持通用)。

### 2.6 渲染管线(自研包的结构)

Iris 规定的包结构 = 一系列着色器程序,按固定顺序执行:

```
shadow(fsh/vsh)        —— 太阳光深度图(可复用;不做我们自己的灯阴影,见 §2.7)
gbuffers_* 系列        —— 世界/实体/手/天空,写入 gcolor/gdepth/normal 等 G-Buffer
                       (自研包做最小集:basics+terrain+entities+hand+skytextured+water+weather+beaconbeam)
composite → compositeN —— 屏幕空间 pass,可读 G-Buffer + SSBO:
                       composite(光照:锥光+SSAO 式遮挡)
                       composite1(体积光 raymarch,1/2 分辨率降采样)
                       composite2(风格:ACES/曝光/颗粒/暗角)
final                  —— 输出+可选 FXAA
```

**自研包的技术选型(与旧项目 B 同构,代码全重写)**:

| 部件 | 方案 | 说明 |
|---|---|---|
| 语言 | `#version 430 core` | 兼容面最广,避免 450 特性陷阱 |
| 光照 pass | composite 前部(需 depthtex1+gbuffer 齐全) | 位置选择:先于任何雾/泛光/色调映射 |
| G-Buffer | depthtex0/1 + normal + albedo(自写最小版) | 不依赖任何第三方包 |
| 风格 | 自写 ACES + 自适应曝光 | **这是原创性的核心资产** |
| 兼容 | 只承诺 Oculus 1.8.0 / Embeddium ≥0.3.31 / Iris 系 | 不做 OptiFine 兼容(它不支持 composite 外部 SSBO) |

### 2.7 光照积分与遮挡

**表面照明(composite,逐片元)**:

```
radiance = Σ light:  ndl × diffuse(BDDF) × spot(软边) × atten(§2.3) × visibility(遮挡) × color
最终 = 表面反照 × radiance + 环境光 + 高光(镜面)
```

各部分:
- **diffuse**:Fd_Burley(或简化 Lambert),粗糙度来自 gbuffer(有法线+粗糙度就做 PBR-ish,否则 Lambert 兜底);
- **高光**:GGX 镜面,只在手电筒方向 ± 反射方向内可见 —— 这是"金属枪身反光"的来源;
- **遮挡(上限 = 屏幕空间)**:从片元向光源方向 8–12 步深度步进(`TorchScreenSpaceShadow` 的思路,自写并改进:步长自适应+`depthtex1` 线性化);**局限**要写进文档:屏幕外的遮挡者无法参与(墙面后面的物体不投阴影)——老项目两次验证此为普通 Iris 包可行上限;
- **环境光**:夜景 = 深蓝黑,随曝光自适应。

**真投影阴影(探索项,不承诺)**:老项目判定"不可行"是在注入路线上(拿不到 Oculus 内部 shadowRenderTargets);自研包**可以**试一个 spike:研究 Iris 是否暴露"自建 shadow camera"或"自定义阴影贴图"能力(部分新 Iris 支持 `shadowMapResolution`、`shadow` 自定义 framebuffer...,版本 1.8.0 需实测)。**写进 spike(S4),验收失败即关闭,不阻塞主线**。

### 2.8 体积光(volumetric beam)

- **原理**:composite1 中,以屏幕每个像素 → 重建世界射线(经过场景相对坐标),沿**锥体空间**内 raymarch:从灯位置沿锥方向采样 8–16 步,用 HG 相位函数(各向异性 g≈0.3–0.6)算散射;
- **只对锥内+距离内的采样计数**,雾/密度、光束强度来自 `vlParams`;
- **成本控制**:1/2 分辨率(或 1/4)+8 步上限+摇动模噪声作 dither;性能预算见 §3.1。
- 关键视觉价值:开灯时,雾/烟尘里的"光柱"是"塔科夫感"最直观的来源。

### 2.9 风格层(原创性的核心)

**这一层决定了"像不像是原创作品"。** 全部自己实现:

1. **色调映射**:ACES(Hill 拟合,参数可调)——高光滚降,避免"平白一片";
2. **自适应曝光**:以画面中位亮度为目标,眼适应时间常数(约 0.3–1.0s),暗场景自动提亮、手电筒聚焦时不过曝;
3. **胶片颗粒 + 暗角 + 可选手动 split-tone**(夜景偏冷、光处偏暖);
4. **风格目标板(tarkovline 的 `docs/02` 法)**:选 4–6 张参考照片(夜景手电场景),定义每张的量化目标(中位亮度、饱和度区间、黑位 0.02–0.05、对比度、色温轴区间),每次调整后**量化对比**验收;
5. **参考设定(草案)**:夜用手电 3500–4000K(暖白),光锥边缘软,环境接近黑但保留暗部细节。

### 2.10 诊断体系(开发机制,保留并升级)

- **时序探针**:DEBUG 编译开关(`#define TACLIGHT_DIAG`)启用 atomicOr 回写入 `reserved` 位掩码(表面进入/距离通过/锥通过/遮挡求值…),Java 侧 100 拍读回解析——**发布版关闭全部探针**;
- **调试绿锥**:K 键 = `FLAG_DEBUG`,GLSL 输出纯绿色锥(忽略材质),截屏肉眼判定;
- **证据集**:每个里程碑 3–5 张固定视角截屏(同机位/同参数),可 A/B 对照;
- **日志**:`TACLIGHT_*` 前缀 单行化,`/taclight diag` 输出打包探测结果。

## 3. 项目边界

### 3.1 资源底线(写死)

| 约束 | 值 |
|---|---|
| 目标平台 | MC 1.20.1 + Forge 47.1.x + Java 17 |
| 渲染栈 | Oculus 1.8.0 + Embeddium ≥0.3.31(不支持 OptiFine) |
| 性能底线 | GTX 1060 级 @1080p,平均 60FPS(不开体积光 ≥90FPS) |

### 8.7 实测调优·亮度-距离耦合与世界空间锚定(2026-08-27)
- **亮度-距离正相关(√ 耦合)**:物理依据 = 反平方律下等照度线距离 d ∝ √I——更亮的光天然照更远。实现:`有效半径 = radius(基准) × √(finalIntensity/6.0)`,钳制 ≤ radiusMax(96);基准半径默认 40→56。**未来"挡位"设计原则**:挡位只改亮度,照距随 √ 自动缩放,不需要独立的距离档位。
- **第三人称/世界空间锚定**:手持灯原点原锚相机(第三人称下灯浮在相机上);改为第一人称锚相机(原行为)、非第一人称锚玩家眼睛+玩家视线。这是"Handheld Moon 型"世界空间效果的行为层前提;**可见光锥体积感本体 = M3**(composite1 raymarch,已批准,SSBO `vlParams`/`beamDensity` 字段已预留)。
- **Handheld Moon 参考定位**(用户提供的对照实现):该 mod = 原版光照地图(LambDynamicLights 系动态光源)+ 自绘"第三人称光束"实体 + 屏幕滤镜层,许可 **ARR**(0 行照搬红线加重:仅允许参考行为语义)。映射到本项目:"地面亮斑" = M1 锥光照明;"世界中可见光锥" = M3 体积光束;"他人可见" = v2(见下注)。技术路线不同但视觉目标同型,且我们的路线由光影包权威渲染,合法原创。
- **v2 他人光源可行性注记**(更新 §3.3#4 的实现认知):手持手电是原版物品 → 其他玩家的"手持状态"经 vanilla 实体同步天然可见,**他人手电锥光可纯客户端实现,无需网络包**;枪灯(TaCZ)开关状态无原版同步,才真正需要网络协议。维持 v2 边界不变,但实现成本比原估低。
- **近场软肩压缩(实机反馈:近场过曝糊死)**:诊断 = 反平方归一化造成近场"平台"(1/4 半径处仍有 83% 亮度)+ M0 无高光压缩 → 加法混色削顶成纯绿;属真实亮度曲线缺陷而非调试色问题,M1 继承同款公式会同样糊。修复 = `taclight_soft_knee(x)=x/(1+G·x)`(G=2.0,斜率设计:远场 f≈x 几乎不动、近场压向 1/G;近远比 5.3:1→2.6:1),合成增益 1.5→1.8 补偿远场。**可调旋钮 = `TACLIGHT_KNEE_GAIN`**(lib/taclight_common.glsl):调大近场更压、对比更大。参考 v0.8.2 同型软膝行为语义,公式重写;M1 高光压缩复用,完整 ACES 仍在 M2。

### 8.8 M1 开发热修记录(2026-08-27)

1. **include 行尾注释炸整包**(区别于着色器编译错误):`#include "/lib/…" // 注释` 被 Iris 按整行解析为路径 → `InvalidPathException: Illegal char <">` → **整个包加载失败、光影被禁用**(pipeline 都建不起来,K 键自然无光)。规则写死:**Iris/Oculus 下 include 指令必须独占一行,行尾禁止任何附加内容**。防复发:`checkShaderIncludes` gradle 契约守护,`syncShaderPack` 强制前置,违规即构建失败。
2. **"无照明"结案与双面法线**(门探针四象限判读):albedo/法线/SSO/ndl 四输入全部健康、门控几何全对(骷髅白斑=全门通过)→ 照明系统实际已工作;"没有照明"是场景误判(平射时地面入射角极浅 ndl≈0.1 属物理正确)+ 植被单面法线缺陷(savanna 草丛交叉面片背面背光)。修复 = `gl_FrontFacing` 背面翻转(7 个 gbuffers);门探针/四象限沉淀为 M1 常备诊断工具(composite.fsh 开关)。**方法论沉淀:实机排查优先做"输入可视化探针",不要靠猜。**
3. **地形法线数据源不可信 → 导数法线**(双面法线后俯射复测:草面片亮、地形顶面仍暗):实体路径同代码正确 ⇒ **Embeddium 区块路径的 gl_Normal 方向错误**(本栈实锤)。修复 = composite 改用深度重建位置的屏幕空间导数求面法线(`cross(dFdx,dFdy)` + 朝向构造校正)——不信任任何外部法线方向,整类法线方向错误被构造性消灭;代价 = 实体低多边形棱面感(M1 接受,M2 风格层评估是否回补属性法线)。
