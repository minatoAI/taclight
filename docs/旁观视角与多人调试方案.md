# 旁观视角与多人调试方案(调研结论 + 提案)

> 日期:2026-08-29。回答三个问题:
> ① 如何增加一个视角,观察模组在玩家身上的效果;
> ② 以 TacLight 为例,如何观察体积光在世界中的位置/形状;
> ③ 从他人视角看,体积光亮度是否干扰他人画面。
> 非编号文档(遵守红线)。配套《调试环境搭建计划 v2》《调试手段调研报告-AI自动化》。

---

## 1. 先说结论(TL;DR)

1. **最关键事实(代码级)**:当前 TacLight 的灯状态是"纯本地,零网络包"(`ClientLightState` 类注释原文),上载器每帧只收集**本地玩家**的最多 2 盏灯(手持+枪灯)。**任何其他玩家的客户端上都不会出现你的体积光束**——多人干扰问题今天还无法测试,因为在观察者的画面里它根本不存在。所以"第二人旁观"分两层:**视角获取**(本报告 §3,当天可做)和**多人可见性**(§4,需要一次真实现,提案 M5)。
2. **视角获取的三级阶梯**:F5 第三人称(已支持,零成本,自检形状)→ Freecam 开发模组(推荐主力,自由环绕观察,注意 §3.2 的相机锚定陷阱)→ **第二客户端实例**(真·他人视角,`--quickPlayMultiplayer` + `--username` 可全自动入服,是测干扰的唯一正解)。
3. **容量不是瓶颈**:SSBO Java 侧 `bufferSize = 16 + 96N` 动态分配,GLSL 侧 `lights[]` unsized array 按头部 `lightCount` 迭代——多人多灯在数据通路上一旦收集即可生效,约束只剩性能(每灯 raymarch),需距离剔除+数量上限。
4. **干扰验收**靠既有工具链即可闭环:观察者实例同机位 on/off 截图 → `imgdiff`/`griddiff`(准星区局部亮度)/`stylemetrics`(SAT/CONTRAST)/`clusterprobe`(晕圈半径)+ DBG 视图 5(bloom 链)检查泛光溢出;加一个新场景 preset `interfere` 和一条 `/taclight light` 命令(命令化开关 = 自动化与同步真源一举两得)。

## 2. 代码级现状(2026-08-29 通读确认)

| 事实 | 位置 | 含义 |
|---|---|---|
| 灯状态纯本地、零网络包 | `client/ClientLightState.java`(类注释"纯本地,零网络包") | 多人下其他客户端拿不到开关状态 |
| 每帧只收集本地玩家的灯,写死 ≤2 | `channel/ClientSpotlightUploader.java#onFrame`(`new ArrayList<>(2)`,只读 `mc.player`) | 观察者 SSBO 里永远没有别人的灯 |
| SSBO 容量两侧均动态 | `channel/SpotlightBufferLayout.java`(`16+96N`)/ `pack/shaders/lib/taclight_common.glsl`(`lights[]` unsized + 头部 lightCount) | 多灯无需改 ABI,只做剔除/上限 |
| 第三人称锚定已支持 | `ClientSpotlightUploader.java` L75-84(fp 分支:第三人称锚玩家眼位+玩家视线,注释明言"第三人称/他人视角需求,Handheld Moon 型") | **F5 自检今天就能用**;多人收集可复用同一条 world-space 数学路径 |
| 枪灯仅本地 | `MuzzlePoseCapture.consumeFresh()`(第一人称渲染事件捕获,本地);第三人称走 else 近似分支 | 他人枪灯可先用近似位姿,精确矩阵列为远期 |
| 无开关灯命令 | `command/TacLightCommand.java` 仅 `/taclight kit` | 自动化只能键注入 L;加命令一举两得(见 §4) |

**一个现成的陷阱(Freecam × 锚定逻辑)**:上载器用 `mc.options.getCameraType().isFirstPerson()` 判定锚点。Freecam 类模组分离相机时相机类型仍是第一人称 → 灯会**锚到观察相机而不是玩家**(灯跟着观察者跑)。规避/修复二选一:
- 操作规避:开 Freecam 前先按 F5 切第三人称(锚定分支变为玩家眼位);
- 代码修复(3 行,建议 P1 顺手):`boolean fp = mc.options.getCameraType().isFirstPerson() && cam.getEntity() == mc.player;`——相机实体不是玩家时一律锚玩家。

## 3. 视角获取方案阶梯

### 3.1 一级:F5 第三人称(零成本,当天可用)

已支持(§2)。用途:自检锥形位置/形状/是否"灯浮在相机上"。局限:仍在本客户端,机位受玩家身体约束,测不了"他人画面"。

### 3.2 二级:Freecam 开发模组(推荐主力观察工具)

- Freecam(CurseForge,1.20.1 Forge 可用)丢进 `run/mods` 即可,零代码;分离相机穿墙飞行,任意角度环绕锥体,配合 DBG 视图 4(colortex4 体积光单独成像)看光束几何,配合 `clusterprobe`(K 霓虹模式)程序化定位锥形簇心/面积。
- 注意 §2 末尾的锚定陷阱(先 F5 或打 3 行补丁)。
- 备选:Spectator Freecam(Modrinth,命令/键位切真旁观模式);远期可在模组内自实现 `/taclight freecam`(客户端命令,免外部依赖),但 dev 期间装现成 mod 更省。

### 3.3 三级:第二客户端实例(真·他人视角,测干扰的唯一正解)

同一台机器跑两个 dev 实例,完全可自动化(原版 1.20+ 启动参数,dev 同一入口):

| 角色 | 启动 | 说明 |
|---|---|---|
| 服务器(推荐) | `gradlew runServer` | dev 专用服,固定端口 25565;`server.properties` 设 `online-mode=false` + `enable-rcon=true`(RCON 口 25575)→ 场景命令走 RCON,不占键鼠 |
| 玩家 A | `runClient --quickPlayMultiplayer 127.0.0.1:25565 --username PlayerA` | 手持设备、开关灯 |
| 观察者 B | `runClient --quickPlayMultiplayer 127.0.0.1:25565 --username ObserverB` + 进服后 `/gamemode spectator` | 只看不动,机位由 `/tp`(或 cam 注册表)固定 |

- 引用:[Quick Play(Minecraft Wiki)](https://minecraft.wiki/w/Quick_Play) —— `--quickPlayMultiplayer <host:port>`、`--username <名字>` 为 1.20+ 原版参数;与计划里已定的 `--quickPlaySingleplayer` 同机制,build.gradle 加一个 `-PtaclightJoin=host:port`/`-PtaclightUser=` 注入即可(模式照抄 QuickPlay 参数方案)。
- **run 目录隔离(必须做)**:两个 runClient 共用 `run/` 会互踩 latest.log/options.txt/screenshots。干净做法:build.gradle 定义第二个 run 配置(如 `clientObserver`,独立 `workingDirectory`,如 `run-observer/`),各自有自己的 oculus.properties(自动选包)/options.txt;`syncShaderPack` 增加同步到 observer 目录。
- GPU 成本:双 Oculus 管线。缓解:场景小(计划固定场景区)+ 观察者实例降渲染距离(8)/锁 60fps;`maxFps:260 + enableVsync:false` 的 preflight 只对被测实例 A 做。
- **drive.ps1 升级点**:两个窗口标题同为"Minecraft* 1.20.1 - 多人游戏",`find` 需支持**按 PID/窗口矩形选定**(Win32 枚举可用),`shot`/`chat` 动作带窗口参数;其余动作集不变。
- LAN 备选:单人实例 A `/publish` 开 LAN、B 直连——免起专用服,但端口随机、无 RCON、日志/端口解析麻烦,自动化不如专用服,列为人工联机时的快捷路。
- Replay Mod:**不适用**——灯状态不在录像数据里,回放无法复现"谁的灯开着"(§4 落地后反而可用,见文末注)。

## 4. 前置缺口:多人可见性(提案 M5,批准后实施)

目标:观察者客户端能看到 A 的手电/枪灯锥体。最小实现,复用现有世界空间路径:

1. **状态真源上服务端**:新增服务端命令 `/taclight light <on|off|toggle> [player]`(注册进 TacLightCommand);状态存玩家实体 `SynchedEntityData`(两个 boolean:手持/枪灯),原版自动同步到所有客户端。L 键保留为"本地切换 + 发包"(或初期先只留命令,键位后接)。命令化同时解决两件事:自动化(chat 注入/RCON 一条直达)与同步真源。
2. **收集端循环**:上载器 `onFrame()` 从"仅本地玩家"改为遍历 `mc.level.players()`,对每个开关灯的玩家复用第三人称分支的锚定数学(`getEyePosition(partialTick)` + `getLookAngle()`,world 直传);本地玩家仍是精确分支。
3. **性能护栏**:距离剔除(默认 ≤48m,config)+ 数量上限(默认 8,config,超出保最近)+ 遍历跳过自身走原路径。raymarch 每灯成本 ×N,场景验证用 `sparkc` 对比 N=1/N=4 帧耗时。
4. **契约与诊断**(沿用项目契约文化):`SpotlightBufferLayoutContract` 补多灯写读回环(`readLight` 已支持 index);diag dump 增加逐灯打印(数量+位置+方向);调试期可按玩家索引微调灯色(现 R/G/B 常量在 `ClientSpotlightUploader` 头部)以肉眼区分"这是谁的灯"。
5. **远期**:他人枪灯精确枪口位姿(复用 `MuzzlePoseMath`,从 TaCZ 远端玩家物品栏+姿态近似),当前用第三人称近似位姿即可满足干扰测试。

工作量估计:核心 1+2+3 约 300-400 行(含契约),与调试计划 P1(场景/机位)可并行。**顺序建议**:P0(键位/骨架)→ M5(可见性)→ P1(场景/机位)+ 干扰协议——没有 M5,§3.3 的观察者实例只能看到"无灯的世界"。

## 5. 干扰验收协议(观察者实例就绪后执行)

**新增场景 preset `interfere`**(进 SceneBuilder/mcfunction 预设表):
A、B 相距 8m 站位,A 面向 B 附近墙面开灯;观察者机位两个:`interfere@behindB`(B 侧后方,看 B 的画面)、`interfere@side`(锥体侧面,看几何)。

**测量流程**(全自动,SOP-1 变体):
```
A 侧:/taclight light on|off(RCON 或 chat 注入,不占键鼠)
B 侧:固定机位 → on/off 各截一张(shot 命令/GDI)
→ tools/imgdiff(on-off 差异热图:确认 B 画面里出现了什么)
→ tools/griddiff(B 准星区/屏幕中心局部 RGB 读数:被直照时是否过曝)
→ tools/stylemetrics(SAT/CONTRAST 变化:B 画面是否被"洗白")
→ DBG 视图 5(bloom 链单独成像,B 侧检查 bloom 溢出/错位)
→ clusterprobe(K 霓虹,从 B 侧量晕圈半径/面积)
→ 有曝光锁 define 时锁曝光测几何,解锁复核真实观感(自适应曝光会放大"洗白"感)
```

**判定标准(提案,数值待首次实测标定)**:
- B 被直照:准星区目标(蜘蛛)仍可辨;无全屏 bloom 晕圈吞没画面;SAT 提升有界(初值建议 ≤25%)。
- B 看锥体侧面:无硬边锯齿/闪烁;锥形对称;密度从侧面看不糊屏。
- B 未被照射(灯朝别处):B 画面中心区亮度变化 ≤ 阈值(初值建议 5%)。
- lightCount 压测:2 玩家×2 设备=4 灯,SSBO 通路与帧耗时回归;溢出行为(上限截断)日志可见。
